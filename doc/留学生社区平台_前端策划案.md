# 留学生社区平台前端策划案

## 一、文档定位
本文件用于指导留学生社区平台前端设计与实现，服务对象为产品经理、UI/UX 设计师、前端开发、测试同学。文档重点不讨论商业模式，而是从前端视角明确：

1. 前端要承接哪些核心业务目标。
2. 第一版 App 需要有哪些页面、组件和交互。
3. 前端与后端接口如何协作。
4. 状态管理、导航结构、适配规范和开发排期如何设计。

## 二、前端目标

### 2.1 产品目标
前端需要把“注册 -> 完善资料 -> 获取推荐 -> 发起聊天 -> 浏览社区 -> 获取信息”这条核心链路做得简单、稳定、可理解。

### 2.2 前端目标
1. 首次打开应用后，用户能在 2 分钟内完成注册和基础资料填写。
2. 首页应在 3 秒内让用户看懂平台价值和下一步动作。
3. 社区、聊天、匹配三个高频页面要做到低学习成本、高可用性。
4. UI 风格统一，支持中、韩、英三语言扩展。
5. 关键页面支持埋点，方便后续迭代。

## 三、产品形态与技术范围

### 3.1 客户端形态
1. 移动端 App：同时具备 Android 端与 iOS 端
2. 管理后台不在本文件核心范围内，仅做简要说明

### 3.2 推荐技术方案
1. 框架：Flutter
2. 状态管理：Riverpod、Bloc 或 Provider 三选一，建议优先选择结构更清晰的方案
3. 路由管理：GoRouter 或同类声明式路由方案
4. 网络请求：Dio
5. 本地存储：SharedPreferences / Secure Storage / Hive
6. 国际化：Flutter Intl 或同类 i18n 方案
7. 图片加载与缓存：cached_network_image

### 3.3 后端协作前提
1. 后端编程语言统一为 Kotlin。
2. 后端框架统一使用 Spring Boot 管理项目服务与接口。
3. 数据存储统一使用 MySQL 数据库。
4. 前端所有接口联调、鉴权逻辑、错误码约定、分页结构和上传流程均以 Kotlin + Spring Boot 提供的 API 规范为准。

### 3.4 MVP 前端范围
1. 登录注册
2. 引导与资料完善
3. 标签选择与状态编辑
4. 首页推荐与匹配详情
5. 私聊与会话列表
6. 社区首页、发帖、帖子详情
7. 信息中心首页、分类页、文章详情
8. 个人中心、认证页、设置页
9. 举报、拉黑、错误提示、空状态

## 四、前端设计原则

### 4.1 低认知负担
页面层级不能太深，首次用户看到每个页面都应知道“这里是什么”和“下一步做什么”。

### 4.2 高信息密度但不拥挤
留学生产品的信息量天然较大，前端要通过卡片、分组、分段标题和标签系统来消化复杂信息，避免大段文字堆叠。

### 4.3 强场景感
首页和匹配页不应只是信息列表，而要体现真实场景，例如“找饭搭子”“今天想聊天”“新生报到攻略”等。

### 4.4 明确反馈
所有关键动作必须有状态反馈，包括提交成功、上传中、审核中、发送失败、重试成功、内容违规等。

### 4.5 国际化优先
所有文本必须从资源文件读取，不允许把中韩英文案写死在组件内部。

## 五、信息架构

### 5.1 底部导航建议
MVP 阶段采用 5 个主 Tab：

1. 首页
2. 社区
3. 发布
4. 消息
5. 我的

### 5.2 一级页面职责
1. 首页：承载匹配推荐、状态入口、快捷信息入口和活动推荐。
2. 社区：承载帖子流、板块切换、搜索入口和发帖浏览。
3. 发布：发帖入口，后续可扩展活动发布。
4. 消息：会话列表、系统通知、未读数。
5. 我的：资料、认证、收藏、设置、语言切换。

### 5.3 二级页面职责
1. 匹配详情页
2. 聊天详情页
3. 帖子详情页
4. 发帖页
5. 文章详情页
6. 标签管理页
7. 认证提交页
8. 设置页

## 六、页面规划

## 6.1 启动与登录流程

### 页面清单
1. Splash 启动页
2. 登录 / 注册页
3. 验证码页
4. 密码设置页
5. 首次引导页

### 页面目标
让用户低门槛进入平台，并尽快开始资料完善。

### 交互要求
1. 启动页只停留短时间，避免多余动画影响首开速度。
2. 登录注册支持邮箱和手机号切换。
3. 验证码输入支持自动聚焦和倒计时。
4. 新用户登录成功后强制进入资料完善流程。

### UI 建议
1. 登录页顶部应直接表达平台定位，如“留学生交友与信息支持平台”。
2. 表单尽量使用短字段和明确占位文案。
3. 新用户和老用户入口应合并，减少分流困惑。

## 6.2 资料完善流程

### 页面清单
1. 基础资料页
2. 学校与专业选择页
3. 兴趣标签选择页
4. 场景标签选择页
5. 当前状态设置页

### 页面目标
让系统尽快获得可用于匹配和推荐的画像信息。

### 交互要求
1. 全流程采用分步式，不宜单页塞入太多字段。
2. 关键步骤需有进度显示。
3. 可暂时跳过部分非必要字段，但必须完成最低资料集。

### 最低资料集
1. 昵称
2. 学校
3. 语言
4. 至少 5 个标签

## 6.3 首页规划

### 页面目标
首页是整个平台最重要的前端页面，需要同时承担“推荐匹配、快捷入口、状态展示、内容引导”四个职责。

### 页面结构建议
1. 顶部问候区
2. 当前状态卡片
3. 匹配推荐卡片区
4. 快捷功能入口区
5. 热门攻略或新生信息区
6. 活动或社区推荐区

### 关键组件
1. 状态切换胶囊
2. 推荐用户卡片
3. 匹配理由标签
4. 快捷入口宫格
5. 信息文章横滑卡片

### 交互要求
1. 推荐卡片点击进入匹配详情。
2. 首页支持下拉刷新。
3. 用户切换状态后，首页推荐可局部刷新。
4. 卡片上应能直接“打招呼”“收藏”“跳过”。

## 6.4 匹配详情页

### 页面目标
帮助用户判断是否值得建立联系。

### 页面内容
1. 头像与昵称
2. 学校、语言、专业等基础资料
3. 兴趣标签与状态标签
4. 匹配理由
5. 自我介绍
6. 操作按钮

### 操作按钮
1. 打招呼
2. 收藏
3. 跳过
4. 举报

### 交互要求
1. 匹配理由必须可读，不只是算法分数。
2. 按钮区在小屏设备上需要固定底部，便于单手操作。

## 6.5 消息模块

### 页面清单
1. 会话列表页
2. 聊天详情页
3. 系统通知页

### 会话列表页要求
1. 展示头像、昵称、最近一条消息、时间、未读数。
2. 支持长按删除、拉黑、举报。
3. 顶部可切换“私聊”和“通知”。

### 聊天详情页要求
1. 支持文字和图片消息。
2. 输入区需要考虑键盘弹起后的布局稳定性。
3. 发送失败要支持重试。
4. 图片消息点击可预览。

### 交互细节
1. 新会话首次进入时可带预设问候语。
2. 被对方拉黑或账号异常时，输入框需禁用并提示原因。

## 6.6 社区模块

### 页面清单
1. 社区首页
2. 板块列表页
3. 帖子详情页
4. 发帖页
5. 搜索页

### 社区首页结构
1. 顶部搜索框
2. 板块切换 Tab
3. 推荐 / 最新 / 关注切换
4. 帖子流

### 帖子卡片字段
1. 作者信息
2. 标题
3. 摘要
4. 图片缩略图
5. 板块标签
6. 点赞、评论、收藏数

### 发帖页要求
1. 标题可选，正文必填。
2. 支持上传图片。
3. 可选择板块与标签。
4. 可开启匿名模式。
5. 提交前进行敏感词预校验。

### 帖子详情页要求
1. 首屏尽量展示完整标题与核心内容。
2. 评论区应支持按时间排序。
3. 楼主身份、认证身份应有弱强调标识。

## 6.7 信息中心模块

### 页面清单
1. 信息中心首页
2. 分类列表页
3. 搜索结果页
4. 文章详情页

### 首页结构
1. 搜索框
2. 分类入口宫格
3. 热门攻略区
4. 最新更新区
5. 官方信息入口区

### 文章详情页要求
1. 显示标题、更新时间、来源。
2. 支持图文混排。
3. 支持收藏、分享、复制链接。
4. 外部官方链接需二次确认跳转。

## 6.8 我的页面

## 八、导航与路由规划

### 8.1 路由结构建议
1. `/splash`
2. `/auth/login`
3. `/onboarding/profile`
4. `/onboarding/tags`
5. `/home`
6. `/match/:id`
7. `/messages`
8. `/chat/:id`
9. `/community`
10. `/post/create`
11. `/post/:id`
12. `/info`
13. `/article/:id`
14. `/me`
15. `/verification`
16. `/settings`

### 8.2 路由策略
1. 登录态失效时自动跳转到登录页。
2. 未完成资料时禁止进入部分核心页面。
3. 深链能力为后续分享帖子和文章预留。
4. Android 端与 iOS 端共用同一套路由结构与业务页面定义，避免双端体验割裂。

## 九、状态管理规划

### 9.1 全局状态
1. 登录态
2. 当前用户资料
3. 语言设置
4. 未读消息数
5. 全局配置

### 9.2 页面级状态
1. 首页推荐列表
2. 社区帖子流
3. 发帖表单
4. 聊天消息列表
5. 信息中心文章列表

### 9.3 状态管理原则
1. 服务端数据优先通过 repository 层统一获取。
2. 页面不直接拼装复杂接口逻辑。
3. 异步状态统一处理 loading、success、empty、error 四类状态。

## 十、接口协作规划

### 10.1 前端接口分层
1. `authApi`
2. `userApi`
3. `matchApi`
4. `messageApi`
5. `communityApi`
6. `articleApi`
7. `reportApi`

### 10.2 前端接口处理要求
1. 统一封装请求头、Token 注入、错误码处理。
2. 文件上传单独封装，支持进度回调。
3. 接口超时、网络异常、鉴权失败要有统一降级提示。
4. 前端接口模型命名、字段解析与分页结构需对齐 Kotlin + Spring Boot + MySQL 的服务端返回规范，避免双端各自定义数据结构。

### 10.3 推荐接口协作方式
1. 首页拉取推荐列表时返回用户卡片和匹配理由。
2. 用户点击跳过后应局部更新列表，不强制整页刷新。
3. 打招呼成功后直接创建会话或跳转聊天页。

## 十一、视觉与交互规范建议

### 11.1 视觉方向
建议采用“清爽、可信、轻社交”的视觉语言，避免过于娱乐化，也不要做得像纯工具软件。

### 11.2 色彩建议
1. 主色：偏稳重的蓝色或青绿色
2. 辅助色：浅灰、米白、浅青
3. 状态色：成功、警告、失败、信息四类标准状态色

### 11.3 字体层级建议
1. 页面标题
2. 模块标题
3. 卡片标题
4. 正文
5. 说明文案
6. 标签和辅助信息

### 11.4 交互细节
1. 所有长列表要有骨架屏或下拉刷新反馈。
2. 空状态页面不能只是留白，要给出下一步建议。
3. 表单报错优先使用字段内提示，不只用 Toast。

## 十二、多语言与适配规范

### 12.1 国际化要求
1. 文本全部走 i18n 资源。
2. 文案长度变化要纳入布局设计。
3. 不同语言下按钮宽度和标题换行要可接受。

### 12.2 适配要求
1. 支持主流全面屏尺寸。
2. 顶部刘海区和底部安全区必须适配。
3. 长文本、长昵称、长学校名不能撑坏布局。

### 12.3 暗黑模式
MVP 阶段可暂不支持，但配色和组件结构建议为后续扩展预留空间。

## 十三、埋点与数据需求

### 13.1 关键埋点事件
1. 打开 App
2. 注册成功
3. 资料填写完成
4. 标签选择完成
5. 点击推荐用户
6. 发起打招呼
7. 进入聊天页
8. 发帖成功
9. 点击文章
10. 收藏文章

### 13.2 前端埋点原则
1. 事件命名统一。
2. 页面曝光与点击事件分开定义。
3. 不在组件内部随意散落埋点逻辑，统一由页面或埋点层管理。

## 十四、异常与边界状态

### 14.1 必须设计的异常页面
1. 无网络
2. 请求失败
3. 空数据
4. 上传失败
5. 认证被拒绝
6. 账号被封禁

### 14.2 关键边界场景
1. 用户资料未完善时访问首页。
2. 推荐列表为空。
3. 聊天对象被封禁或删除。
4. 帖子被删除后仍通过链接访问。
5. 文章内容下线后仍在收藏页存在。

## 十七、结论
前端第一阶段的核心任务不是“做很多页面”，而是把最重要的用户路径做顺：能注册、能完善资料、能看到推荐、能发起聊天、能浏览社区、能找到实用信息。只要这条主链路顺畅，前端就已经为整个项目打下了最关键的产品基础。
